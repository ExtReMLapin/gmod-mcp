# Test matrix

Each scenario is run through the MCP tools (curl or the Claude Code MCP client). Columns: ID, procedure, expected result,
last result (date). Statuses: ✅ green, ❌ red, ⏳ to run.

Procedure conventions: `call <tool> {args}` denotes a `tools/call`; "in game" = after `map_load gm_construct` (singleplayer).
"Persistence across map changes" scenarios are covered globally by **X-01**, which calls all three realms between
ten map changes, and per tool where relevant.


## Final campaign

Two consecutive full passes, each starting from a cold game start (ad-hoc harness, not part of the deliverable): the
functional scenarios of this matrix (session, Lua, console, world, rendering, sound, documentation, X-01 with 10 map
changes), the 75-check hardening battery, and the dedicated-server part (registration, `ambiguous_instance`, relay,
remote LAN machine refused, connection from a hosted game to the local srcds, net message srcds -> client, coordinator
re-election).

| Pass | Result | Date |
|---|---|---|
| A (cold start) | **140/140** ✅ | 2026-11-07 |
| B (cold start, after A) | **140/140** ✅ | 2026-11-07 |

Issues found by the campaign and fixed before these two passes:
- `connect` while the game hosts a map crashed the engine (access violation in `engine.dll`): `console_exec connect`
  now leaves the current game first.
- Back-to-back map transitions (disconnect + maxplayers + map) intermittently crashed the game's embedded Chromium
  (`html_chromium.dll`): `map_load` now waits for the menu's loading screen to close plus ~30 frames before a new load.
- An internal call was refused by the `ambiguous_instance` guard; the menu `status` spammed
  "Tried to look up command maxplayers as if it were a variable".

## Official conformance suite

Run in CI (`tests/conformance/run.py`) against `gmod-mcp-conformance-host`: the module's real MCP/HTTP server code
without the game, the suite's fixture tools/prompts/resources (test-only, `tests/conformance/fixtures.cpp`, never in the
DLL or the bridge) and a relay adding the bearer token. Suite pinned in `tests/conformance/expected-failures.json`
(`0.2.0-alpha.12`), which lists the checks absent by design. 2026-07-28: 37/37 required scenarios pass; 2025-11-25: 22/30,
the 8 others are by design (logging, server-initiated sampling/elicitation, legacy `resources/subscribe`). Not scored
(Tasks extension) and failing: the module's tasks never park for input (`input_required` task status), never report a
protocol-level `failed` task with an `error`, and `tasks/get` does not check `Mcp-Name` (see "Known gaps" below).
The manual run below predates the host.

Fixtures must never ship. `tests/conformance/check_fixtures_absent.py` (CI step "Fixture tools absent from shipped
binaries", before the suite; unit tests in `tests/conformance/test_check_fixtures.py`) enforces it, strongest guarantee
first:

1. **Build graph (deterministic, the primary guarantee).** The CMake File API (`codemodel-v2`, requested before configure
   by a workflow step; the script requests it and re-configures once if a local build directory has no reply) lists each
   target's sources and include directories, on the Visual Studio generator (Windows leg) as on Makefiles or Ninja
   (Linux leg). No source under `tests/conformance/` may belong to a target other than `gmod-mcp-conformance-host`, and no
   other target may have that directory on its include path.
2. **Sources.** No fixture name (or the canary) as a string literal in `src/`, `loader/`, `plugin/`; no
   `mcp::set_request_hooks` call there.
3. **Binary scan (secondary).** The module and the bridge contain no fixture name and not the canary
   `GMOD_MCP_CONFORMANCE_FIXTURE_CANARY_7f3c9a1e`, a long string the host defines (`conformance_host.cpp`) and prints for
   `--version`. The host must contain it: that proves the scan sees the host's own strings. Short fixture names are only
   counted, for information: GCC may build them from immediate stores, so they are not always contiguous bytes (a first
   version required 80% of them and failed on the Linux leg with 47 of 63), and a short name leaked into the module could
   be invisible too, which is why the scan is not the guarantee.

While the host runs, its relay gives every local process that can reach its loopback port an authenticated session
(the relay adds the bearer token), including the module's real tools (`game_terminate`, native `lua_file_write` and
`lua_file_delete`, `wiki_*`). CI and development only, never shipped; do not run it next to a live game you care about.
