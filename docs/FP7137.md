# Workarounds for Garry's Mod issue 7137

Everything gmod-mcp does to avoid the engine bug [Facepunch/garrysmod-issues#7137][engine] (and to say so to the
agent) lives behind the tag `FP7137`: `git grep FP7137` finds every line. When Facepunch fixes the bug, remove the
workarounds with the steps given for each section. Related report on this repository: [#2][issue2].

[engine]: https://github.com/Facepunch/garrysmod-issues/issues/7137
[issue2]: https://github.com/ExtReMLapin/gmod-mcp/issues/2

## The bug

Starting any new 64-bit game process (`gmod_win64.exe` or `bin/win64/gmod.exe`) makes every other running Garry's Mod release and restore all its D3D9 resources.
The cycle starts about 0.3 s after the new process is created and lasts 2-10 s; the main thread of the other games is
blocked meanwhile (MCP calls to them time out). A game whose map load ends inside that window draws its dynamic mesh
without a vertex buffer and crashes in `shaderapidx9.dll+0xd79a`.

## Launch/map_load lock (B4, B5)

### Behaviour

- **Lock shared by every bridge of the user** (B4). Each bridge process (one per client session) records what it
  does in `<user config>/gmod-mcp/fp7137.state`, guarded by an OS file lock (`fp7137.lock`, released by the OS when a
  process dies). Entries: `L` = a launch is creating game processes, `M` = a map load is running; plus the time of the
  last game process creation.
  - `instances_launch` waits while any entry `M` exists, then registers `L` while it creates the processes, and
    records the creation time of each. It also waits while any game reports a map load in progress that no entry `M`
    explains (issue #7, below).
  - `map_load` through the bridge (any target instance) waits while an entry `L` exists and until the settle delay
    (15 s) after the last process creation, then registers `M` until the load ends. For a map load run as an MCP task
    the bridge polls `tasks/get` and releases the entry when the task is no longer `working`.
  - `instances_launch {map}` registers an `M` entry for each map it loads.
- **No stale lock.** Every entry carries its owner's pid and start stamp, and an expiry (the call's `timeout_s`, plus
  10 s for map loads). A dead or reused owner, or a passed expiry, drops the entry the next time anybody reads the file.
  A damaged file counts as empty.
- **Reporting.** A call that waited carries `waited_s` and `waited_reason` in its result (structuredContent and its
  text twin; in the task's `statusMessage` for a map load run as a task; per instance for `instances_launch {map}`).
  While it waits, the bridge sends `notifications/progress` (progress = seconds waited) when the client gave a
  progress token, and shifts the game's own progress values by the wait so they keep increasing.
- **Loads the bridge does not see** (issue #7). A map load started by the console (`map`, `changelevel`), Lua
  (`RunConsoleCommand`), a script talking HTTP to a game, or a user, registers nowhere in the state file. Each module
  therefore reports `loading` in its heartbeat (see "How a game knows it is loading" below) and `instances_list` shows it.
  Before it registers `L`, `instances_launch` asks `instances_list` (a probe given to `Gate::enter`, about every 500 ms
  while it waits, outside the file lock) and waits while any running instance has `loading: true` and no entry `M` is
  registered. `waited_reason` then starts with `map_load_outside_bridge` and names the instances; the error at the timeout
  is the same `map_load_in_progress`. `map_load` through the bridge does not wait for such loads (only launches matter) but
  lists the other instances that were loading when it started as `other_games_loading` (the target instance excluded).
  When the game cannot be reached the probe is empty: no extra wait. The kill switch disables all of it.
- **How a game knows it is loading.** `src/loadflag.h` (a pure `Tracker`) with two sources. Server: set when a new
  server Lua state appears (`note_map_load_start`, called by the module's `gmod13_open` in the new server state, or by the
  pump as a fallback), cleared when `map_loaded` is published or on `disconnected`. Menu: the menu state's
  `IsInLoading()` (`menu_idle`), polled by the pump every 5 frames in client mode. Both cover loads from any origin since
  they follow the engine, not the tool. A source that never reports its end stops counting after 300 s. The flag is in
  `self_info()` (`loading`) and `coordinator::wake()` sends a heartbeat at once when it changes, so the coordinator knows
  within a fraction of a second instead of up to 2 s later. `status.loading` still reads the menu's `IsInLoading()` on the
  main thread (unchanged). Limit: a load that starts and ends between two pump frames, or inside the first fraction of
  a second, can be missed; a game whose main thread is blocked by a long load still answers its heartbeat (own thread).
- **Bounded wait.** The wait is limited by the call's `timeout_s` (default 180). A wait whose end is known (the settle
  delay) and lies beyond the timeout fails at once; otherwise it fails when the timeout is reached. The error is
  `map_load_in_progress` (launch blocked by a map load) or `launch_in_progress` (map load blocked by a launch or by
  the settle delay), with `waited_s`; nothing was started or sent to the game.
- **Staggering** (B5). `instances_launch {map}` no longer loads all its maps at once: each load goes through the same
  gate (so it starts after the settle delay that follows the last process start) and at most 2 maps load at a time
  (`kMaxParallelMaps`). The cap is global, not per call: every map load of every bridge (`instances_launch {map}` and
  `map_load`) registers an `M` entry, and a load waits while 2 others are registered (the live entries of the state file are
  counted: a dead owner or an expired entry does not). A launch of 2 clients, another launch of 2 and a `map_load` therefore
  never have more than 2 games loading together (they had 5). The wait is bounded like the others (`map_load_in_progress`
  at the timeout) and the kill switch lifts the cap. A load that had to wait reports `waited_s` / `waited_reason` in its
  `instances[i]` entry.
- **Kill switch:** the environment variable `GMOD_MCP_FP7137_WORKAROUND=0` disables the whole thing (default on).
  `GMOD_MCP_FP7137_SETTLE_MS` overrides the settle delay (tests only).

Limits: the bridge only delays its own calls. A game the user starts by hand, or a game without gmod-mcp (no `-mcp`), is
not seen and cannot be held back; a map load started by the console or a script while a launch is creating its processes
or within the settle delay after one is not held back either. A waiting `instances_launch` can be starved by a steady flow of map loads (it fails at its
timeout). A `map_load` run as a task makes the bridge wait before it answers with the task, so the client sees the
task id late.

### Removal

1. Delete `src/bridge/fp7137.h`, `src/bridge/fp7137.cpp`, `src/loadflag.h`, `tests/native/test_fp7137.cpp`.
2. In `src/bridge/bridge.cpp`, delete every line tagged `FP7137`, and the helper functions
   `fp7137_gate_map_load`, `fp7137_finish_map_load` and `fp7137_loading_games`. In `src/agent.cpp`, `src/agent.h`,
   `src/coordinator.cpp` and `src/coordinator.h` delete the lines tagged `FP7137` (the `loading` flag, the menu poll, the
   `loading` key of `self_info`, `wake` and its use in the heartbeat loop; drop the `coordinator.h` / `loadflag.h`
   includes from `agent.cpp` if nothing else needs them). In `src/tools_instances.cpp` drop `loading (...)` from the
   description of `instances_list`. In `launch_tool`, the lines between the tags restore the
   plain flow; the map loads of `instances_launch {map}` go back to one thread per instance, all at once (the `std::vector<std::thread> th;` / `th.emplace_back` / `join` code replaced by `fp7137::for_each_limited`; git history shows it). In `handle_request`, the relay call goes back to `[](const json &m) { out(m); }`, and
   in `progress` the `g_fp7137_progress_offset` term goes.
3. In `CMakeLists.txt`, drop the lines tagged `FP7137`; in `tests/native/unittests_main.cpp` the `test_fp7137` lines.
4. In `tests/bridge/test_bridge.py` delete `case_fp7137`, its helpers (`fp_*`), the `FP7137 tests` lines of the fake
   server and the `fp7137` entries of `CASES` / `DEFAULT`; in `tests/native/fake_game.cpp` the `GMCP_FAKE_PID_DIR` block.
5. Deleting the state files (`fp7137.state`, `fp7137.lock`) is optional: nothing reads them any more.
6. Remove this section, the CHANGELOG entry, and the TESTS.md rows tagged FP7137; then run `git grep FP7137`: nothing
   must remain except this file's history.

README. They say: starting a game makes the other games release their GPU resources for 2-10 s and a map load ending
then crashes (A1); what the bridge serialises, `waited_s` / `waited_reason`, the errors `map_load_in_progress` /
