# Workarounds for Garry's Mod issue 7137

Everything gmod-mcp does to avoid the engine bug [Facepunch/garrysmod-issues#7137][engine] (and to say so to the
agent) lives behind the tag `FP7137`: `git grep FP7137` finds every line. When Facepunch fixes the bug, remove the
workarounds with the steps given for each section. Related report on this repository: [#2][issue2].

[engine]: https://github.com/Facepunch/garrysmod-issues/issues/7137
[issue2]: https://github.com/ExtReMLapin/gmod-mcp/issues/2

## The bug

Starting any new `gmod_win64.exe` makes every other running Garry's Mod release and restore all its D3D9 resources.
The cycle starts about 0.3 s after the new process is created and lasts 2-10 s; the main thread of the other games is
blocked meanwhile (MCP calls to them time out). A game whose map load ends inside that window draws its dynamic mesh
without a vertex buffer and crashes in `shaderapidx9.dll+0xd79a`.

## Launch/map_load lock (B4, B5)

### Behaviour

- **Lock shared by every bridge of the user** (B4). Each bridge process (one per client session) records what it
  does in `<user config>/gmod-mcp/fp7137.state`, guarded by an OS file lock (`fp7137.lock`, released by the OS when a
  process dies). Entries: `L` = a launch is creating game processes, `M` = a map load is running; plus the time of the
  last game process creation.
  - `instances_launch` waits while any entry `M` exists, then registers `L` while it creates the processes, and
    records the creation time of each.
  - `map_load` through the bridge (any target instance) waits while an entry `L` exists and until the settle delay
    (15 s) after the last process creation, then registers `M` until the load ends. For a map load run as an MCP task
    the bridge polls `tasks/get` and releases the entry when the task is no longer `working`.
  - `instances_launch {map}` registers an `M` entry for each map it loads.
- **No stale lock.** Every entry carries its owner's pid and start stamp, and an expiry (the call's `timeout_s`, plus
  10 s for map loads). A dead or reused owner, or a passed expiry, drops the entry the next time anybody reads the file.
  A damaged file counts as empty.
- **Reporting.** A call that waited carries `waited_s` and `waited_reason` in its result (structuredContent and its
  text twin; in the task's `statusMessage` for a map load run as a task; per instance for `instances_launch {map}`).
  While it waits, the bridge sends `notifications/progress` (progress = seconds waited) when the client gave a
  progress token, and shifts the game's own progress values by the wait so they keep increasing.
- **Bounded wait.** The wait is limited by the call's `timeout_s` (default 180). A wait whose end is known (the settle
  delay) and lies beyond the timeout fails at once; otherwise it fails when the timeout is reached. The error is
  `map_load_in_progress` (launch blocked by a map load) or `launch_in_progress` (map load blocked by a launch or by
  the settle delay), with `waited_s`; nothing was started or sent to the game.
- **Staggering** (B5). `instances_launch {map}` no longer loads all its maps at once: each load goes through the same
  gate (so it starts after the settle delay that follows the last process start) and at most 2 maps load at a time
  (`kMaxParallelMaps`). A load that had to wait reports `waited_s` / `waited_reason` in its `instances[i]` entry.
- **Kill switch:** the environment variable `GMOD_MCP_FP7137_WORKAROUND=0` disables the whole thing (default on).
  `GMOD_MCP_FP7137_SETTLE_MS` overrides the settle delay (tests only).

Limits: only what goes through a bridge is known. A game the user starts by hand, or a map load the user or an addon
triggers, is not seen. A waiting `instances_launch` can be starved by a steady flow of map loads (it fails at its
timeout). A `map_load` run as a task makes the bridge wait before it answers with the task, so the client sees the
task id late.

### Removal

1. Delete `src/bridge/fp7137.h`, `src/bridge/fp7137.cpp`, `tests/native/test_fp7137.cpp`.
2. In `src/bridge/bridge.cpp`, delete every line tagged `FP7137`, and the two helper functions
   `fp7137_gate_map_load` and `fp7137_finish_map_load`. In `launch_tool`, the lines between the tags restore the
   plain flow; the map loads of `instances_launch {map}` go back to one thread per instance, all at once (the `std::vector<std::thread> th;` / `th.emplace_back` / `join` code replaced by `fp7137::for_each_limited`; git history shows it). In `handle_request`, the relay call goes back to `[](const json &m) { out(m); }`, and
   in `progress` the `g_fp7137_progress_offset` term goes.
3. In `CMakeLists.txt`, drop the lines tagged `FP7137`; in `tests/native/unittests_main.cpp` the `test_fp7137` lines.
4. In `tests/bridge/test_bridge.py` delete `case_fp7137`, its helpers (`fp_*`), the `FP7137 tests` lines of the fake
   server and the `fp7137` entries of `CASES` / `DEFAULT`; in `tests/native/fake_game.cpp` the `GMCP_FAKE_PID_DIR` block.
5. Deleting the state files (`fp7137.state`, `fp7137.lock`) is optional: nothing reads them any more.
6. Remove this section, the CHANGELOG entry, and the TESTS.md rows tagged FP7137; then run `git grep FP7137`: nothing
   must remain except this file's history.
